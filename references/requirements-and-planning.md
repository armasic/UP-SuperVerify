# 需求与验证策划

## 来源和基线

记录设计版本、配置、接口、输入资料的版本/位置及权威关系。用户指定的规范与补充决定为判据依据；“更新日期较新”“名称含 final”或 RTL 已如此实现不自动裁决冲突。保存需求条目的来源定位，不复制整本手册到报告。

已有合格 LRS 复用原 ID；没有时从需求、手册和设计说明整理需求表：ID、行为或指标、适用条件、来源、确认状态、问题。明确要求、分析推导和建议分别标记；已批准补充说明成为新的来源记录。未知行为不能补成“忽略”“清零”或“报错”。允许集合按集合与禁止副作用检查。

需求表回答设计应做什么，验证表回答怎样证明；实现行为是待验证对象。无 RTL 仍可形成方案，但接口/可观察量不明的部分标为待补，不虚构层次路径。只阻塞依赖未决项的变体，其他已明确工作继续。

## 正向发现交互

从来源识别适用的参与者、目标选择、模式、权限、操作、数据边界、故障位置、并发时序、复位与恢复。每个交互说明共享哪个状态、资源、仲裁或错误路径；记录候选、入选、排除和阻塞。已有三维或更高阶依赖不能只用两两组合代替。

小且有界的相关空间可穷举，非法项也记录原因；空间大时按风险、边界、优先级和故障机制选取，说明残余范围。等价类要有依据，模式条件、接收者角色、写入生效边界或错误处理变化不能被同一代表值掩盖。

case 共用步骤，变体给出具体参数、初始状态、对象、输入和事件顺序；随机测试明确合法约束、分布目的、oracle 与命中统计。不能先写几项普通用例再附加所有需求 ID 宣称全面覆盖。

## 独立检查点与缺陷可观测性

每个 CP 明确对象、观察量、采样事件/窗口、方法和来源需求。逐变体填写明确预期。每个 CP 可独立失败；一条多信号关系可以是一个 CP，响应、计数、状态、隔离和恢复各自正确不能合成一句“均正确”。

高风险测试逐项说明：假设缺陷、激活条件、激活证据、正确与缺陷实现的可观察差异、判定 CP，以及正常对照。必要时植入一个可控缺陷检查检测链，按风险选择，不要求所有项目建立通用 mutation 框架。

例：校验错误命令被 A/B 选中，C 未选中。分别检查 A/B 未提交、错误状态符合规范、C 的提交和状态保持；检查故障到达有效接收点，合法对照能提交，后续事务能恢复。只看 error 置位会漏掉“报错仍提交”；只看没有提交又会让“所有命令丢弃”假通过。没有物理或模型依据时，不套用该例的接收者或故障注入点。

## 寄存器与数值行为

按来源盘点地址、字段、访问属性、复位、编码、生效时点、副作用和依赖。逐字段评价访问与功能，按需要评价复位和保持。RW 回读不能代替配置生效；RO 不安排无依据的写入预期；W1C/RC/自清零要先真实触发状态再检查清除，事件与清除竞争按来源展开。字段可按等价机制分组，但保留各字段到具体变体/CP/动作的映射。

数值模型明确位宽、有符号性、舍入、截断、饱和/回绕、容差和初始化。来源未定义的溢出或极端值保持未决；避免从 DUT 代码直接翻译出同样错误的参考模型。只检查非零、非 0xFF 或已知值时，结论限于该观测，不宣称精确数值正确。

## 吞吐、延迟与完成条件

吞吐定义有效输入/完成数据、净载荷或总线位、计量窗口、预热排除、工作配置和上下游负载。背压测试区分 DUT 限制与环境限流。延迟定义起点、终点、握手接受条件、是否包含等待、采样沿及周期/时间单位；有变化时报告适用的范围或统计，不能只取最好值。

每项必验需求关联具体变体和实际检查器；未映射、阻塞、排除分别可见。验收条件由项目指定：必过需求、适用配置、覆盖目标、吞吐/延迟门槛、缺陷关闭与豁免。没有通用的固定测试数或覆盖百分比可替代这些条件。

方案发出前，从来源正向查到变体，再从变体反查条件和 oracle。检查输入遗漏、高阶交互、非目标隔离、未知预期、寄存器功能效果和过宽等价类。脚本只检查已经声明的关系；没有写入模型的遗漏需要这种语义审阅发现。
