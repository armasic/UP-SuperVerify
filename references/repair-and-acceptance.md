# 修复 回归与验收

## 失败分类

先保留准确源、配置、种子、输入序列、日志和观察点，再定位第一个偏离。区分 DUT 缺陷、测试/参考模型错误、工具环境故障和规格未明确。最小复现要保留导致问题的交互条件，不能去掉背压、并发或初始化状态后声称原缺陷消失。

规格已明确且修复在授权范围内时，直接组织 RTL 或测试修复。模型/预期修订记录独立的规范依据和原因；不能仅因 DUT 输出不同就更新 golden。需要改变外部接口、数值语义、吞吐/延迟目标或项目范围时，先给用户具体影响和选项；不依赖该决定的工作继续。

修复后先证明原失败被解决，再验证受影响行为、邻近边界及必要集成路径。永久保留有价值的失败输入作为回归。独立检查器或适用对照应能区分缺陷版和修复版；“改了之后不报错”本身不足以证明修复正确。

## 输入变化与证据

计划、源码、参数、文件列表、测试环境、golden 或工具条件改变后，定位受影响依赖并标记证据需重验。旧结果仍保留其原输入范围；不能重命名报告让它看起来属于新版本。

运行记录和摘要分开保留，最终选中的证据必须对应同一交付基线；历史缺陷版失败不抹除，也不要求它在修复后“变通过”。最终验收使用修复基线的有效回归，仍需检查是否存在该基线尚未解决的失败。

文件哈希有助于核对身份，但不会证明一个自然语言需求正确，也不能仅凭日志哈希断言日志内容真实通过。审阅实际检查与结果、来源和覆盖分母，是自动化脚本之外的工作。

## 产品验收硬规则

| 状态 | 含义 |
| --- | --- |
| 计划完成 | 适用需求已有具体测试和判据，未决与排除可见 |
| 测试已实现 | 用例/检查器存在并完成适用自检 |
| 实际已执行 | 对指定输入完成有效运行，结果可查 |
| 阶段交付 | 已达到本次选定终点，后续或未完成项仍明确 |
| 产品验收通过 | 全部必验需求、适用覆盖和性能目标满足，必要修复及回归关闭，证据属于交付基线 |

**已有用例全过但关键需求没有有效测试时，产品验收保持未完成。** 没有实际检查、样本为零、未知用例、超时、编译/运行错误、未解释 SKIP、陈旧证据和未定义 oracle 都不能算通过。

通过/失败/未运行/证据不足/获准排除分别记录。阶段交付可以带缺口；报告不能把它改称产品验收完成。豁免和排除有明确条件、理由、批准来源与有效期/版本范围，不能为提高覆盖率任意缩小分母。重大验收风险同时出现在正文。

## 连续推进与停止

复用已有授权，按“证据差距→下一任务→实施验证→复核”推进。批次或一次试验失败后调整有依据的诊断，不把“本轮结束”作为整个任务完成。规划/复核可由独立 Agent 承担；同一文件按所有权修改，主代理核查真实产物而非只接受完成声明。

具体项目先记录整体目标、本次终点与预算。总预算或时间边界到达时汇报实际结果、关键差距及继续成本；必要外部条件或产品语义变更交给用户决定。不要在没有新证据目的时无限重复，不把工作记录文件当作后台持续运行保证。

## 交付检查

从每个必验需求查到计划、检查器、实际 PASS 与有效源身份；从覆盖未命中和性能测量反查适用条件；从缺陷记录查到修复输入及回归结果。测试结果齐全后仍做来源与语义审阅。任何一条关系缺失，结论保持对应未完成，具体下一步应能说明如何消除该缺口。
