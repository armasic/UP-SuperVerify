# 正式验证交付

## 正文结构

报告面向其他工程师或验收者，采用简洁正文与完整明细附件。标题明确项目、用途和版本，开头直接给结论与适用范围。表格用于可比较的记录，长说明用短段落；不按固定页数删减测试。

1. **验证策略**说明范围、关键风险、独立判据和选择测试方法的理由。针对适用的复位、协议、异常、并发、吞吐和延迟，给出覆盖与退出条件。
2. **验证方案**把 LRS ID 映射到用例、变体和检查点，写出前置条件、刺激次序、采样边沿、预期，以及如何发现典型缺陷。列出要留原始波形的关键检查点。
3. **验证结果**对照同一批 ID 写当前基线的实测、结论及证据。放入关键用例的实测波形、工具及配置、修复回归、覆盖分母、豁免和缺口。正文开头可先概述验收结论。

原始仿真波形随证据保存，用查看器从该次运行导出清晰 PNG，保留导出命令或信号布局与时间窗口。图上应能读出信号名、时标和参与判断的值。图注给出 LRS、用例/变体、检查点、运行、刺激/采样时刻、预期与实测。示意时序图用于讲解设计。计划要求的实测波形缺失时，在报告中逐项标明。复核者应能打开原始波形，在所列窗口重读同一结果。

版本、签署和修订信息按交付方实际要求提供，不机械制造多页空表。正式文件不带对话过程、生成过程说明、助手自评分或“请您确认”等聊天残留。重要状态和限制属于报告本身，不能为了精炼删除。

## 明细与去重

完整验证表至少保存需求/case/变体/CP ID、来源引用、公共配置引用与本例差异、具体刺激顺序、对象、采样窗口、预期、实现入口、实际运行与观察、结果及证据。各 CP 独立判断；一个大段“响应/数据/状态均正确”不可替代明细。

公共初始化和同族步骤写一次；变体保留所有独立差异。将重复的限制集中编号，局部引用，正文保留会影响验收的项目。日志、波形与数据库放证据附件，以编号定位，不逐段粘贴。完整用例表不在索引、正文小节和表题里反复复制。

验证方案说明预定检查，验证报告说明实际检查与结果；二者可由同一台账生成，但不得因方案有预期就填“通过”。结果表不得用用户输入的摘要覆盖实际评价。通过率不改称覆盖率；没有覆盖采集或对应报告时写未采集/证据不足。其他批次的数值保留其来源，不混入本次统计。

## 文件与工具

默认正式文档提供可编辑 Word，定稿 PDF 按交付要求生成；完整明细可独立 CSV/表格，保留结构化台账和复现材料。用户提供模板时复用其必要栏目与设计，参数按当前项目填写。

模块正式交付在计划中填写 `module_report`，从该字段选取标题和文件名后缀。将第四份文档与需求规格书、LRS、设计文档的文件名、文内版本和修订信息核对。RTL/TB 采用工程约定的文件名及其实际哈希。开发期间可用阶段报告，交付前将 `latest/` 指向真实修订并核对最终回归。项目已有封面或人工修订时，另生成候选文件，按栏目合入并核对原稿。

```sh
python3 scripts/render_report.py --root MODULE --plan verification/plan.json \
  --results verification/results.json --output MODULE/docs/验证文档_v0p1.docx
```

机器契约见[数据契约](data-contract.md)。导出器用同一套检查生成正文和完整 CSV，Word 嵌入图像，Markdown 以相对路径引用图像。示例命令使用新项目首版，明细附件为 `验证文档-details_v0p1.csv`。原有独立验证台账可继续使用。报告状态来自本次证据检查，Word 和 PDF 按交付方要求制作。

Word 创建/修改采用宿主可用文档能力；有捆绑依赖加载工具时先解析运行时，不擅自在项目安装库。使用实际渲染结果检查标题、字体、表头、分页、长行、缺字和空页，必要时调整后重渲染。没有渲染或 PDF 工具时准确说明哪个格式/检查未完成，不把未查看的文件称作视觉验收通过。

若中文在导出的页面中显示为空白或方框，为当前渲染进程指定可用的中文字体，再重新查看页面和波形图注。

## 最终核对

读者应能快速回答：验证了哪个版本、哪些要求、实际结果如何、修复了什么、什么尚未验证、怎样复现。正文结论与附件数据一致，引用可打开，证据来自最终交付输入。对外材料不包含凭据、许可值、私有绝对机器路径或不必要的内部日志。
